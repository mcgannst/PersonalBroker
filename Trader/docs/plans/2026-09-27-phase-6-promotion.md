## Key decisions (resolved here; Stephen can overturn any of them, see Open questions)

**D1. Clean trading day.** A session day D is **clean** when, at evaluation time, every job expected for D (the table below) **finally succeeded before its deadline**, the 9:35 event `event:orb_open` fired within its late grace, and D has no `outage` mark. Precisely:
- A job's status for D is `succeeded` if **any** `job_runs` row for `(job, D)` has `status = 'succeeded'` and `finished_at ≤ deadline` (for `event:*` rows: `started_at ≤ deadline`, because the scheduler judges lateness by when an event fires, and the 9:35 scan itself may take up to a minute; a slow scan that started inside its grace is on time). So a failed attempt followed by a successful in-process retry (P5-T15), a successful worker/cron race loser, or a **manual catch-up after a deploy that succeeds before the deadline** are all clean. Reason: the BRD reliability NFR says jobs are retried and re-run safely; what matters to trading is that the work was done in time and nothing was missed. This also matches the P5 planner's note (a job counts as failed only when its latest row is failed) while not letting a later forced re-run that fails spoil an on-time success.
- `late` (a success only after the deadline), `failed` (the latest row failed and the deadline has passed, or a `running` row is still there at the deadline), `missing` (no row at all by the deadline, e.g. the container was down), and for `event:orb_open` `missed` (an error starting `missed:`) each make D **not clean**.
- Before a job's deadline, a failed or missing job is `pending` (it may still be retried or caught up); D's verdict is `pending` while any check is pending and none has failed for good.
- `token-refresh` writes no `job_runs` row: D gets a `token-refresh` check that fails when an `error` event with source `questrade.token` (runtime `TOKEN_SOURCE`) was written after the previous session's close and by D 18:00 ET, **unless** a `succeeded` row of a job that needs a working token (`premarket`, `event:orb_open` or `postclose` for D) **started after the last such event**. It succeeds when there is no such event. (Verifier fix: `api_credentials.last_refresh_at` holds only the latest refresh, so it can't say whether the chain recovered before a *past* day's close, and a day's verdict must never change on re-evaluation just because time moved on.)
- **Retries (P5-T15/T17):** the in-process retries of `nightly`, `premarket`, `preopen`, `postclose` and `weekly` (at most 3 attempts, waits of `jobs.retry_delay_seconds` × 1, × 2) never start a wait that would end after their `RetryPolicy` deadline: 09:18 ET for `premarket` and 09:28 ET for `preopen` (P5-T17 wiring). The soak deadlines below are later than those retry deadlines on purpose, so an attempt started just before its retry deadline still counts when it succeeds.
- Replay runs never write `job_runs` (P5 decision 3), so they never affect the soak.
- An **outage** (the worker heartbeat stale or `/api/health` not 200 for more than 5 minutes between 09:30 ET and D's close, known to the orchestrator from its checks or a deploy) makes D not clean even if every job succeeded; the orchestrator records it with `trader soak-mark outage`. A deliberate restart shorter than 2 minutes (P5-T18 LIVE 6, the market-hours restart test) is **not** an outage: it is the recovery behaviour the soak should prove, and the day stays clean if no job fails or is missed.

**D2. Redeploys during the soak.** A deploy **does not reset** the clean-day count unless it is a **trading change**. A deploy is a trading change when its diff (the previously deployed dev commit → the new one) does any of:
1. changes a default or allowed range of a trading setting (`RuntimeSettings` fields other than the `reports.*`, `web.*`, `telegram.*`, `jobs.*`, `preopen.*`, `postclose.*`, `replay.*`, `logging.*` groups; adding a new key to those groups is not a change either) or a strategy's default params;
2. changes the time or command of an existing `docker/crontab` line of a SPEC §9 trading job (token-refresh, nightly, premarket, preopen, event, checkin, postclose), or the events a strategy schedules. Adding a reporting line (P5-T17's `weekly`, T2's two `soak-report` lines) is not a trading change;
3. **modifies** (not only adds) code on the live decision path (`trader/strategies/`, `trader/engine/`, `trader/broker/`, `trader/market/`, `trader/jobs/nightly.py`, `trader/jobs/premarket.py`, `trader/adapters/claude/catalyst.py`, `trader/settings_store.py`) such that an existing assertion in `tests/engine/`, `tests/strategies/`, `tests/broker/`, `tests/market/`, `tests/jobs/` or `tests/integration/` had to change (new tests alone don't count).

The **P5-T18 deploy** (the first one of the soak, expected on a weekday evening or the weekend) is classified by the same rules: P5 open question 9 expects it not to reset (its engine and broker changes are replay additions); if a P5 fix round modified a decision-path file such that an existing assertion changed (for example in `trader/engine/killswitch.py`), it is a trading change and resets.

Replay-only additions (P5's `on_candles` hooks), job retries, logging, reports, web, API reads and message text are not trading changes.

**The decision log (T9–T12, amendment) is not a trading change,** because it is logging only: it reads the rows the engine already writes and writes nothing but `decision_log`; no decision-path module imports it. The orchestrator confirms this for the T11 deploy (T11 LIVE 1) before recording it as "not a trading change (decision log, logging only)": (a) the diff since the last dev deploy modifies no decision-path file except the **added** `reports.decisions_*` fields in `trader/settings_store.py` (the `reports.*` group is exempt under rule 1); (b) no existing assertion in the rule-3 test folders changed except `MAY_CHANGE` in `tests/integration/test_replay_isolation.py` gaining `decision_log` (a table allow-list for a new run-scoped table, not trading behaviour: stated here so it is not a rule-3 hit); (c) `git diff <previous deploy>..<new> -- Trader/app/tests/replay/golden/` is empty; (d) T10's tests 13–15 ("decisions unchanged with logging on", replay and live) pass in the gate. If any check fails, the deploy is classified as a trading change and resets the count (`soak-mark reset`). **The GitHub workflow cut-over (T13/T14)** changes how the image is built and started, not what it does: deploy mechanics, not a trading change; its deploys are ordinary dev deploys for D3 (catch-up) and the outage rule. The orchestrator classifies every dev deploy in the soak ledger with the rule number and a one-line reason; a trading change is recorded with `trader soak-mark reset --date <first session running the new code>`, so the count restarts at that session (it counts as day 1 if clean). The day of an outage is not clean (D1). **Deploys stay out of 09:15–16:30 ET on session days** unless a fix is urgent (a job would otherwise fail or a position be left unprotected); an urgent in-hours deploy is marked `outage` for that day if it breaks D1.

**D3. Deploy downtime catch-up (Stephen, 2026-09-27).** Deploys (dev and prod) happen whenever ready; nobody waits for a gap between cron lines. After every deploy: take the downtime window that `deploy.sh` now prints (T6), run `uv --directory Trader/app run python ../build/cron_gap.py --from <down> --to <up> --container <trader-dev|trader>` to list the crontab lines that fell in it, run each listed command by hand exactly as printed (`docker --context shared-docker-server exec <container> trader <args> --date <session>`; the jobs are single-flight and idempotent), and confirm its `job_runs` row `succeeded` (for `token-refresh`, its `ok; chain last extended …` line). **Interrupted jobs (P6-T6 fix round 1):** a job still running at `down from` is killed by the recreate but fired before the window, so it is not in that list. `cron_gap.py` also prints, on stderr, every cron job that started in the `--lookback` minutes (default 120) before the down stamp as "may have been interrupted"; for each, and in any case, check `job_runs` (`GET /api/jobs`, the System page) for rows **started before the down stamp** whose status is still `running` or is `failed`, and re-run the printed command (same `--date`) for each one; a row that `succeeded` needs nothing. **After the T14 cut-over** every deploy is a run of the `trader-deploy` workflow: its job summary prints the `down from`/`up at` stamps and the `cron_gap.py` lines for the window (computed on the runner inside the new image), and the orchestrator still runs each listed command by hand from the Mac through the Docker context (no secret is needed for `docker exec`) and confirms the rows. The printed `--date` matters: without it `trader nightly` targets the session after *today* and the session jobs use *today's* ET date, so a catch-up after midnight would run for the wrong session. A line whose window has already passed (`premarket` after 09:30 ET needs `--force` and would only spend Claude budget; `event orb_open` after its grace only records `missed`) is not run: the day is already not clean under D1, and the ledger says so. Record everything in the soak ledger.

**Behaviour and decisions:**
- **Read-only:** `soak-report` never goes through `run_job` and never writes `job_runs`, `settings`, `runs`, `strategy_configs` or anything else; its only writes are the `notifications` row of the one message the notifier sends (and, like every CLI command after P5-T17, a log-mirror `event_log` row if it logs an error line itself). It is not in `ManualJob`, the Dashboard timeline or the System page's job list (none of those change).
- **Plan (verifier fix):** `runtime.plan_builder` is **not** usable here: it calls `get_live_run` (which creates a live run when none is active), `StrategyRegistry.ensure_defaults()` and `report_plan_problems` (which writes relayed `error` events, so evaluating 20 past sessions could send Telegram alerts about old days). `SoakDeps.plan` is built from `scheduler.live_day_plan` with `runtime.active_live_run_id(factory)` (no active live run → `day_plan` of the enabled strategies with no exits-only ones) and the current `RuntimeSettings`; it never reports plan problems. The plan uses today's strategy configs for past days too (an approximation that can only drop events a since-disabled strategy scheduled; `orb_open` is covered by `orb_required`).
- **Window:** the last `--sessions` sessions up to `--through` (default: the latest session whose ET date ≤ today). The consecutive count is taken over the final days in order: `clean` +1, `not_clean` → 0, a `reset` mark sets it to 0 before its day is evaluated. It stops at the first `pending` day (shown as provisional, never counted). `last_final` is the last final day; `earliest_finish` is the session on which the count would reach the target if every later day is clean (`None` once reached).
- Days before the soak started (no container, e.g. Fri 2026-09-25) come out `not_clean` (missing jobs) and simply cap the count; no start date is needed.
- **Now vs deadlines:** a check whose deadline is in the future is `pending` unless it already succeeded. The weekly job makes the week's last session `pending` until Saturday 12:00 ET; the Friday 18:05 line says "weekly report due Sat" and the Saturday `--final` line settles it.
- **Telegram line** (`--notify`): for the evaluated session (`through`) it sends one line, e.g. `Soak Mon 28 Sep: clean ✅ · 9:35 scan 31 s · 1 clean day in a row (target 10) · earliest finish Fri 9 Oct`, or `Soak Tue 29 Sep: NOT clean ❌ preopen failed (TokenExpired…) · count 0 · earliest finish Tue 13 Oct`. It also names any earlier day in the window that has become final since the previous line with a verdict other than the one that line showed (`changed`, e.g. "Mon 28 Sep is now not clean: postclose failed"). `changed` is re-derived, not stored: `load_report` evaluates the window a second time with `now` = the `sent_at` of the latest `notifications` row whose `dedupe_key` starts with `soak:` and compares the two (no previous line → nothing changed). Dates are written as weekday, day and month; times are MT. With `env == "prod"` the prefix is `Ops` and the target and finish date are left out. When `orb_sip` is disabled the 9:35 part reads "9:35 scan off". Nothing is sent when Telegram is not configured (prints "Telegram not configured").
- **Dedupe:** `soak:<date>` for the weekday line and `soak:<date>:final` for Saturday's; a second cron run or a manual `--notify` for the same date sends nothing (the notifier's contract). `--final` on a weekday is allowed (manual use) and uses the `:final` key.
- **Marks:** `soak-mark` rows are `info` events, so the relay never sends them (it relays `error`/`critical` only) and the log mirror ignores them. `load_report` reads them from `event_log` (source `soak`), applies `effective_marks`, and an `outage` mark makes that day `not_clean` with the reason shown.
- **Masking:** every error text in the report, the JSON and the message goes through `redact_text` and is cut to 200 characters; `--json` never includes job `detail` payloads other than the orb-open seconds.
- **Expected set verification:** see D1; the builder adjusts `DEADLINES` only as D1 allows and notes it here.

### Amendment design notes: the decision log (read before T9–T12)

**What exists already (reused, not duplicated).** Almost every decision is already a row: `catalysts` (the Claude grade, direction, quality and `reason` = the rationale, `gap_pct`, headlines, model, cost), the `premarket` job's `job_runs.detail` (`screens[]` with `label`, `filter`, `rows`, `matched` tickers; `screen_errors`, `over_cap`, `budget_hit`), `universe_snapshots` (per symbol `source`, `price`, `avg_volume`, `atr14`) and the `nightly` detail, `candidates` (the top `top_n` ranked names with `rvol`, `rank`, the opening candle, `passed`, `reject_reason` and `data`), the `strategy.orb_sip` notes in `event_log` (skipped scans, the symbols without an opening bar and why, no baseline), `signals` (`intent`, `evidence`, `evidence.rejection` = the risk check, `evidence.sizing`), `proposals` (`sizing`, `status`, `decided_via`, `decided_at`, `decided_by`, `decision_latency_ms`, `expires_at`, `error` "entry blocked: …"), `orders` (`reason`, `cancel_reason`), `fills` (`price`, `slippage`, `fees`, `quote_snapshot`), `trades` (`exit_reason`, `pnl`, `pnl_r`), `kill_switch_events`, and the `strategy.spy_overlay` decision events. What is **not** stored anywhere: why each of the other ~800 universe names was dropped at 9:35 (no opening bar, no baseline, `rvol` below the minimum, outside the top N), the value and threshold of **every** filter for a ranked name (the strategy stops at the first failing rule), which parameter revision was in effect, the planned-versus-fill difference, and a per-day summary.

**Storage decision: a new table `decision_log` (migration 0007), not `event_log`.** Reasons: (1) `event_log` is the operations and alert stream: the relay scans it (levels `error`/`critical`), the System page lists it, the SSE change feed watermarks it and the log mirror writes to it; ~1,000 rows per session would bury real alerts and slow those scans; (2) decisions need typed, indexed columns (`run_id`, `session_date`, `stage`, `symbol_id`, `outcome`, `rule`) for a one-day browse and CSV, which `event_log` lacks; (3) retention differs (decisions are kept for tuning, replay decisions briefly); (4) the per-filter breakdown must be computed with the parameters in effect at 9:35 and frozen once the day is final, so a later config edit can't rewrite history. The table is a **derived journal**: the recorder builds it from the authoritative rows above plus the stored opening bars, and writes nothing else. That is what makes it logging-only (D2).

**How it records "while the app runs".** The recorder is idempotent per (run, session): a pass takes a transaction advisory lock, compares a fingerprint of the day's source rows with the one stored on the day's `day` row, and when something changed rebuilds that run's day in one transaction (delete, insert). Passes run: after the pre-market job and after a cron-fired event (best effort), every `reports.decisions_refresh_seconds` from the worker during the session (never while an `event:*` job is running, so the 9:35 scan is never contended), and a final pass in the post-close, which freezes the day (`final = true`); replays run a final pass at the end of each replayed session under the replay's own `run_id`. Volume: ≈ 800 `scan` rows plus ≈ 50 pre-market rows and a handful of trading rows per session, ≤ ~1 MB/day (≈ 250 MB/year at the cap; typical far less). Retention: live 400 days, replay 30 days (settings), pruned by the post-close.

- **`explain_orb`** evaluates every rule independently, in the strategy's order: `rvol ≥ rvol_min`, `rank ≤ top_n`, not held, no working entry, `direction` bullish (bearish, doji with `doji_body_pct_max`, malformed), `price_min ≤ close ≤ price_max`, `atr14` present, `atr14 ≥ min_atr`, `avg_volume ≥ min_avg_volume`, stop valid (`0 < stop_loss < entry`, from `entry_offset` and `stop_atr_fraction`), catalyst present and classified (when `require_catalyst`), catalyst not bearish, `quality ≥ catalyst_min_quality`, a slot left (`lower_rank`); `first_failure` maps the first failing check to the strategy's rule names (`bearish_candle`, `doji`, `malformed_bar`, `price_out_of_range`, `atr_missing`, `atr_below_min`, `avg_volume_below_min`, `stop_invalid`, `already_held`, `entry_working`, `catalyst_missing`, `catalyst_bearish`, `catalyst_low_quality`, `lower_rank`). It reuses `trader.market.indicators` (`rvol`, `is_bearish`, `is_doji`) and never imports `OrbSip` itself. Three checks depend on the engine's state at 9:35, which no row stores (open positions, working entries, slots left: `OrbSip._orb` on trunk): "not held", "no working entry" and "a slot left" are therefore taken from the candidate's stored `reject_reason` (`already_held`, `entry_working`, `lower_rank`: failed; any later rule or passed: passed; value and threshold `None`, `data.source = "reject_reason"`), while every other check is recomputed from the stored values. The catalyst checks use the `catalysts` row of D (the strategy evaluates them only for names that survived the price, ATR, volume and stop rules, so for an earlier failure they are shown but can't change `first_failure`).
- **`signal`**: per `signals` row: strategy key (via `strategy_config_id`), `event_key`, the intent (type, order type, stop, limit, `stop_loss`, reason), the evidence without the candle; outcome `proposed`, `rejected` (then also a **`risk`** row: rule = `evidence.rejection.check`, reason, detail, sizing) or `error` (`evidence.error`, masked).
- **`proposal`**: per proposal: kind, qty, entry (order spec stop or limit), `stop_loss`, `target` (null), `r_per_share`, `risk_dollars` = qty × `r_per_share`, the sizing (`equity`, `risk_pct`, `risk_dollars`, `shares_risk`, `shares_cash`, `limited_by`), `est_cost` = qty × entry, `est_cost_buffered` = × (1 + `slippage_buffer`), `est_fees` (the fee function `SimBroker` uses for fills if it is a pure function the builder can call read-only; else commission + ECN per share × qty from the settings, labelled `estimate`), `expires_at`; outcome `proposed`.
- **`approval`**: per decided or expired proposal: `approved` (via `telegram`/`web`, "manual"), `auto_approved`, `declined` (`rejected` by Stephen), `expired`, `blocked` (`error` starting "entry blocked", rule = the kill switch), `error` (`failed`); data `decided_via`, `decided_by`, `decided_at`, `decision_latency_ms`, `escalations`, `expired_at`.
- **`order`**: per order: purpose, type, qty, stop/limit, status; outcome `submitted` (working), `filled` or `cancelled` with rule = `cancel_reason`.
- **`fill`**: per fill: `planned_price` (the order's stop for stop orders, limit for limits; for market orders the reference price in `quote_snapshot`, the builder names the key it uses), `fill_price`, `diff_per_share` signed so that **positive = worse than planned** (buy: fill − planned; sell: planned − fill), `diff_total` = × qty, the model `slippage`, fees, the quote essentials (bid, ask, last, quote age), seconds from submit to fill; outcome `filled`.
- **`exit`**: per trade: `rule` = the exit category mapped from `exit_reason`: `protective_stop` → `stop`, `flatten_close` → `flatten`, `overlay_negative` → `overlay`, a kill-switch flatten → `kill_switch`, an expiry auto-flatten → `expiry`, a replay forced close → `replay_close`, anything else → `other` (the builder pins the complete mapping from every reason string on trunk; a new reason fails the test until mapped); reason = the raw `exit_reason`; data entry/exit price, qty, `pnl`, `pnl_r`, `planned_risk`, fees, slippage, minutes held, `unprotected_seconds`; outcome `exited`.
- **`overlay`**: per `strategy.spy_overlay` event of D with a `decision`; **`kill_switch`**: per `kill_switch_events` row tripped or reset on D (`tripped`/`reset`, rule = switch, value, threshold, masked reset reason).
- **`day`**: one row: `DaySummary` in `data` (plus `text` = `summary_text(link=None)` and the source `fingerprint`), outcome `info`, `final` flag.
- **Passes:** `record_day` returns `skipped="disabled"` when `reports.decisions_enabled` is off, `"not_session"` for a non-session, `"final"` when the day row is final (unless `rebuild`), `"unchanged"` when the fingerprint (per run-scoped source table: count and max id of R's rows for D; `catalysts` by D only (not run-scoped); `event_log` only the sources the recorder reads (`strategy.orb_sip`, `strategy.spy_overlay`) for R and D, never the whole table, which the log mirror and alerts keep growing; the count of D's stored opening bars; the latest `nightly`/`premarket` row ids; `reports.decisions_scan_detail`) matches the stored one. Otherwise it rebuilds R's day in one transaction under `pg_advisory_xact_lock(hashtext('trader.decisions:<run>:<date>'))`. **The `final` and fingerprint checks are made after taking that lock, inside the same transaction** (verifier fix): otherwise a worker-loop pass that read "not final" just before the post-close's final pass committed could rebuild the day with `final = false` and un-freeze it. `final=True` marks every row final. Database work never blocks an event loop: the whole pass (reads, lock, delete, insert) runs in one `asyncio.to_thread` call with its own session.
- **Safety:** masks every text with `redact_text`; caps `reason` at 500 characters and each `data` at 8 KB (long lists truncated with a `truncated: n` marker); reads only; writes only `decision_log`; never calls Questrade, Claude, Telegram or FinViz; takes time only from `deps.clock`; raises on database errors (callers isolate them).
- **`summary_text`**: at most 3 lines and 400 characters, e.g. `812 scanned · 14 ranked · 1 passed (NVDA) · 1 proposal, approved by you in 42 s · filled 10.27 vs 10.25 planned (+0.02) · exit flatten +0.8R · top rejects: rvol_below_min 790, catalyst_low_quality 6, doji 3`; times MT when shown.
- **`prune`**: deletes live-run rows with `session_date` older than `reports.decisions_retention_days` (ET today) and rows of replay runs finished more than `reports.decisions_replay_retention_days` ago, in batches of 5,000; returns the counts.
