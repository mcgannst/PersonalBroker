## Imports and constructors
- `from trader.options.prompts import DbPromptStore, PromptSender, button_choices, link_choices, needs_web, prompt_path, TEXT_CHOICES`
- `DbPromptStore(factory, clock)`: the `PromptStore`; every method is its own short transaction, all sync.
- `PromptSender(store, notifier, issuer, renderer, chat_id, settings, clock)` with `async send_due(now) -> int`.
  - `chat_id`: `int | None`; `None` means Telegram is not configured (nothing sent or marked).
  - `settings`: `Callable[[], OptionSettings]`, read on every call.
  - `issuer`: any `CallbackIssuer`; in production the `DbCallbackIssuer` built with the same `CallbackSigner` as the stock worker's bot.
- `from trader.options.messages import OptionMessages`; `OptionMessages(public_base_url)` is the `OptionRenderer`.

## How an answer reaches a strategy
- A Telegram tap or the web route calls `store.answer(prompt_id, choice, text=..., via="telegram"|"web", actor=...)` -> `AnswerResult` with status `ok`, `already`, `unknown`, `invalid_choice` or `text_required`.
- The row becomes `answered` with `delivered_at` NULL. The host's `deliver_answers` reads `store.undelivered(source)` (oldest first), calls the plug-in's `on_answer`, then `store.mark_delivered(id)`.
- `answer_text` is stored stripped; None when empty.

## Messages
Every renderer method returns an `OutboundMessage` for `Notifier.send`. Callers pass raw values.

| Method | Kind | Dedupe key |
|---|---|---|
| `fill(fill, structure)` | `fill` | `opt:fill:<order id>` |
| `lifecycle(event)` | `alert` | `opt:life:<event id>` |
| `alert(source, kind, message, dedupe_key)` | `alert` | `opt:alert:<dedupe_key>` |
| `prompt(prompt, buttons)` | `alert` | `opt:prompt:<id>:<send_count+1>` |
| `summary(view)` | `daily_summary` | `opt:summary:<date>` (first line is the account value) |

- `fill` takes contract labels from `structure.positions`: pass the structure as it is AFTER the fill.
- Times are Mountain Time; links go to `<base>/options`.

## Prompts in Telegram
- A choice is a signed button unless it needs the web: `w` always, and `a` when `needs_text` is true. Those appear as a link to `/options?prompt=<id>` (**the Options page should open that prompt from the query string: T16 checks T15 does**).
- Each send issues a fresh nonce with no expiry. A tap after an answer says "Already answered".
- **T12 calls `sender.send_due(clock.now())` in its loop.**

## Bot dispatch
- `CallbackKind` gained `prompt`; code `o`; ref is the prompt id; actions `a r y n c o h b s k`.
- `TelegramBot._callback` routes `prompt` to `_prompt_tap`, which builds `DbPromptStore(self.factory, self.clock)` itself and answers with actor `telegram:<from id>`.
- **T16 has no bot wiring to do.** The stock worker's bot handles prompt taps once deployed (the stock worker restarts on deploy anyway).

## Gotchas
- `ensure` returns the existing row unchanged whatever its status: a cancelled or answered `dedupe_key` is never asked again. **T11 must use a new key to re-ask** (include a date or cycle number).
- `ensure` raises `ValueError` for an unknown or duplicate choice code, an empty choice list, a `dedupe_key` empty or over 150 characters, or a `default_choice` not among the choices.
- `cancel(dedupe_key)` only affects a pending prompt.
- `pending()` and `undelivered()` are not filtered by run; only `due_for_send` is (active runs only).
- A failed Telegram send is not retried until the next repeat interval (the prompt stays on the Options page).
- The prompt store does not take the book lock (a prompt changes no cash, order, structure or position).
